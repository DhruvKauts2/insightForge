# ADR-0011: Distributed Tracing with Correlation IDs

**Date:** 2026-05-16  
**Status:** Accepted

## Context

InsightForge simulates and ingests logs from seven services (auth, payment, user, notification, inventory, order, shipping). A single user-facing transaction (e.g., placing an order) spans multiple services and generates log entries in each. Without a mechanism to link these entries, debugging a failed transaction requires manually correlating timestamps and service names across thousands of log lines. We need a lightweight tracing strategy that does not require adopting a full distributed tracing backend (Jaeger, Zipkin, Tempo) at this stage.

## Decision

Propagate a `correlation_id` UUID through all log entries that belong to the same logical transaction. Log entries optionally carry `transaction_position` (1-based index) and `transaction_total` (total steps in the transaction) to reconstruct the sequence. A separate `request_id` (generated by `RequestIDMiddleware` per HTTP request to the API) tracks API-layer requests independently.

The `GET /api/v1/correlation/{correlation_id}` endpoint retrieves all log entries sharing a correlation ID from Elasticsearch, sorted by timestamp. The `GET /api/v1/trace/{request_id}` endpoint retrieves entries for a specific API request.

The log generator (`log_generator/generator.py`) demonstrates the pattern by creating multi-step transaction sequences with shared correlation IDs.

## Consequences

**Positive**
- No external tracing infrastructure required; Elasticsearch serves as the trace store via a field filter query.
- `transaction_position` and `transaction_total` allow the UI to render a waterfall-style transaction view in the future.
- `RequestIDMiddleware` ensures every API request is trackable end-to-end from the client header to the log entry.
- The approach is language-agnostic: any service that includes `correlation_id` in its log payload is automatically compatible.

**Negative**
- Correlation IDs must be generated and propagated by the application code in every upstream service; there is no automatic instrumentation (unlike OpenTelemetry).
- No span timing data: we can reconstruct which services participated in a transaction but not how long each step took relative to the others.
- No sampling strategy: every log entry is stored, which at high volume means Elasticsearch stores far more trace data than a sampling-based system (e.g., OpenTelemetry with 1% sampling) would.
- If a service forgets to propagate `correlation_id`, the trace chain breaks silently — there is no validation or alerting for missing correlation IDs.
- Long-term, adopting OpenTelemetry would give spans, parent-child relationships, and compatibility with standard tracing UIs without reimplementing trace semantics.
